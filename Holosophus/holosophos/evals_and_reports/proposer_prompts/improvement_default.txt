## How to think (do this internally before writing JSON)
For each of the {{num_proposals}} proposals, work through these steps:

1. Identify which sub-claim of the Bit you are attacking. Quote the exact phrase.
2. Generate the Flip mechanism. Be specific about: which model component, which training signal, which data source changes.
3. Stress-test feasibility: can this run on ≤8xA100 for ≤7 days, or via public APIs at <$500? If not, scale it down until it can.
4. Stress-test novelty: is this just a known technique with a new name? If yes, discard and regenerate.
5. Pick one experiment that *would falsify* the proposal if it failed, and name the metric, the dataset, and the threshold.
6. Diversify: across the {{num_proposals}} proposals, attack different sub-claims of the Bit. Avoid near-duplicates.

## Required content per proposal

Each proposal must contain:
- chain_of_reasoning (≥5 sentences): walk through steps 1-5 above for this idea, in prose. This is the part a reviewer reads first.
- flip (≥2 sentences): the mechanism, with named components.
- spark (4-6 words): handle for the idea.
- abstract (~250 words, conference style): motivation → method → expected result → significance.
- experiments (list of strings): each experiment must specify (a) dataset by name (e.g. "GSM8K", "ImageNet-1k val"), (b) baseline by name, (c) primary metric, (d) the effect size or comparison that would constitute success. Avoid phrases like "standard benchmarks" or "common datasets" — name them.
- risks_and_limitations (list of strings): include at least one *falsification criterion* — a concrete observation that would force you to abandon the idea (e.g. "if accuracy on GSM8K drops below the 7B baseline by >2 pts, the hypothesis is rejected").
