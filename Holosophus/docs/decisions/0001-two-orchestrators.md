# 0001. Keep both CodeArkt and Claude Code as first-class orchestrators

- **Status**: Superseded by [0008](0008-retire-codearkt-orchestrator.md)
- **Date**: 2026-04-15
- **Deciders**: project lead

## Context

Holosophus started on the CodeArkt runtime — a CodeAct loop that runs Python
`<execute>` blocks per turn against an OpenRouter-backed LLM. After Claude
Sonnet 4 / Opus 4 became viable as agentic models with native sub-agent and
MCP support, we added a parallel orchestrator path built on the Claude Agent
SDK (`scripts/run_research.py`) so that users with a Claude subscription
could run the same research pipeline without OpenRouter spend.

The two paths share:
- MCP toolservers (academia, mle_kit, paperbanana) — same Docker images.
- Eval datasets in `holosophos/evals_and_reports/data/`.
- Manager system prompt source (`system.yaml`) and specialist prompts via
  the canonical YAML schema (see ADR 0002).

They differ in:
- Agent loop format (CodeAct `<execute>` blocks vs. native tool calling).
- Specialist prompt files (`prompts/<agent>.yaml` `codearkt` section
  vs. autogenerated `.claude/agents/<agent>.md` from the `claude_code` section).
- Observability (Langfuse v2 on port 3000 for CodeArkt; Langfuse v3 on 3001
  via langsmith → OTel bridge for Claude Code).
- Compose stacks (`docker-compose.yml` full vs. `docker-compose.mcp.yml` MCP-only).

The recurring question is whether to deprecate CodeArkt now that Claude Code
covers most usage. The answer is no — at least not yet.

## Decision

Both orchestrators stay first-class. Any prompt or agent change must apply to
both paths. The canonical YAML schema (see ADR 0002) carries the shared
content in `canon`, with orchestrator-specific tail in `codearkt` and
`claude_code` sections. The Claude Code entry points
(`scripts/run_research.py`, `scripts/run_eval_claude_code.py`) regenerate
`.claude/agents/*.md` from YAML at startup; the CodeArkt side is loaded
directly via `PromptStorage.compose`.

Refactors that intentionally affect only one path must say so explicitly in
the PR description and not silently bit-rot the other.

## Consequences

- Two specialist prompt files per agent (the YAML section split). Mitigated by
  the canonical-YAML approach: most rules live in `canon` and are written once.
- Two eval runner sets — but both consume the same dataset, so additions to
  the dataset benefit both immediately.
- Two observability stacks need to be operational for full coverage. We accept
  the disk and process cost (Langfuse v2 + v3 coexist).
- Contributors edit prompt YAML; `.claude/agents/*.md` is gitignored and
  regenerated at runtime, so there is no manual sync step and no drift gate.
- We cannot pick one orchestrator and delete the other without re-opening
  this ADR. Casual phrasing of CodeArkt as "legacy" is an anti-pattern (see
  `docs/agent_rules/anti-patterns.md`).
