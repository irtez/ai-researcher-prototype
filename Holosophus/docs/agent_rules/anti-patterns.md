# Anti-patterns

Append-only log of project-specific mistakes that an agent (or developer) must
not repeat (T1.4 in the AI-Native Practices reference, kept outside this repo).
Each entry is incident-driven and gets a stable `AP-NN` id so other docs,
prompts, and the build-loop can reference it by number.

## How to add an entry

- Add a rule when the **same mistake has been made twice**, or once if it was
  costly enough to prevent the second occurrence. Don't pre-emptively log
  hypothetical mistakes.
- Append with the next free `AP-NN` number. **Never renumber or delete** an
  entry — supersede it in place (mark it and link the replacement). The stable
  number is the point.
- Each entry has four fields: **What goes wrong** / **Why it's bad** / **What to
  do instead** / **Mechanical guard** (the test, smoke, or make target that
  catches a regression — omit only if none exists yet).
- Prefer a mechanical guard over a prose rule. If a rule grows a long rationale,
  move it to an ADR (`docs/decisions/`) and leave the imperative here.

---

## AP-01: Don't hand-edit generated `.claude/agents/*.md`

**What goes wrong**: Editing a generated agent file directly.
**Why it's bad**: Those files are autogenerated by `scripts/sync_claude_agents.py`
from `holosophos/holosophos/prompts/<agent>.yaml`. The directory is gitignored
and regenerated by the Claude Code entry points (`run_research.py`,
`run_eval_claude_code.py`) on every invocation, so manual edits vanish on the
next run.
**What to do instead**: Edit the YAML in `holosophos/holosophos/prompts/` and run
the pipeline — the `.md` regenerates itself. To inspect rendered output without
running the pipeline, use `make sync-agents`. **Exception**: files matching the
`dev-*` prefix are hand-written, committed developer-harness agents (see
`.gitignore` and `iter_research_agent_paths` in `run_research.py`); those you DO
edit by hand, and they are deliberately hidden from research runs.
**Mechanical guard**: `python scripts/sync_claude_agents.py --check` reports drift
between YAML and the generated `.md` files.

## AP-02: Don't duplicate `system.yaml` content into `CLAUDE.md`

**What goes wrong**: Copying research-manager runtime instructions into the dev
harness file.
**Why it's bad**: `system.yaml` is the canonical research-manager runtime prompt
loaded by both orchestrators. `CLAUDE.md` is the developer harness for sessions
that work on the codebase. Mixing them confused new sessions into thinking they
were the research manager when opening Claude Code in `Holosophus/`.
**What to do instead**: Research-manager rules go to `system.yaml`; developer
rules go to `CLAUDE.md` and `docs/agent_rules/`.
**Mechanical guard**: none yet — reviewer-checked.

## AP-03: Use `uv`, not `pip` or `.venv`

**What goes wrong**: Running `python -m venv .venv` or `pip install`.
**Why it's bad**: The project standardised on `uv` for reproducible installs and
lockfile management. A stray venv or pip install ends up with a different
resolver and breaks `make validate` on the next contributor's checkout.
**What to do instead**: `uv sync`, `uv run <cmd>`, `uvx <tool>`. Never edit
`requirements*.txt` directly.
**Mechanical guard**: `make validate` runs under the `uv` environment.

## AP-04: CodeArkt and Claude Code are both first-class

> **SUPERSEDED by [ADR-0008](../decisions/0008-retire-codearkt-orchestrator.md) (2026-08-18).**
> CodeArkt is retired as a target for new work; new changes do **not** owe it parity. The entry is
> kept in place — the incident it records really happened, and `AP-NN` numbers are stable. What still
> holds: don't *delete* the vendored runtime or the `codearkt:` YAML sections, and don't strand the
> eval runners that still depend on it (ADR-0008 Consequences).

**What goes wrong**: Framing CodeArkt (or Claude Code) as "legacy" and proposing
deletions.
**Why it's bad**: The project supports two orchestration runtimes (CodeArkt for
the OpenRouter-backed CodeAct loop, Claude Code for the native Claude Agent SDK).
Past PRs framed CodeArkt as legacy and broke the CodeArkt eval pipeline some
users rely on.
**What to do instead**: Any prompt or agent change must apply to both paths
(canonical YAML covers it via the `canon` section; sync regenerates
`.claude/agents/*.md`). Refactors touching only one path must be explicitly
scoped in the PR.
**Mechanical guard**: CodeArkt and Claude Code eval runners (`run_*_eval.py`).

## AP-05: Real end-to-end verification, not just lint/typecheck

**What goes wrong**: Claiming "fixed X" from a green `make validate` or a snapshot
diff alone.
**Why it's bad**: `make validate` checks formatting and type signatures; it does
not exercise the runtime path. Past "fixes" passed validate but failed in the
real research session because the bug was in MCP tool routing or prompt content,
not code structure.
**What to do instead**: Every "fixed X" must show output from a real run that
exercises X — smoke (`make smoke`), an eval subset, or a session log.
**Mechanical guard**: `make smoke`, `make smoke-e2e`.

## AP-06: Don't hardcode `/root` in remote-GPU tools

**What goes wrong**: Writing a remote path as `/root/...`.
**Why it's bad**: cloud.ru ML Space instances run as `jovyan` with
`$HOME=/home/jovyan`, not root. A hardcoded `/root` worked silently for Vast and
broke immediately on cloud.ru (`Permission denied`, `No such directory`). Fixed
in ADR-0006 by routing every remote path through `instance.remote_home`.
**What to do instead**: Any new rsync target, `remote_bash` working dir, or
`remote_text_editor` path must read `instance.remote_home` from the
`InstanceInfo` returned by `get_instance()`.
**Mechanical guard**: `cloudru_smoke.py`.

## AP-07: Don't assume the remote side has rsync

**What goes wrong**: Removing the `scp` fallback from `recieve_rsync` /
`send_rsync`.
**Why it's bad**: `rsync` requires the binary on **both** ends. Vast.ai images
ship it; cloud.ru ML Space jovyan instances do not (no apt cache, outbound HTTP
to the ubuntu archive blocked). The functions try rsync, then fall back to
`scp -r`. Removing the fallback re-breaks cloud.ru.
**What to do instead**: Keep both branches (rsync first, scp fallback) and
surface a clear error combining both stderrs.
**Mechanical guard**: `file_transfer_roundtrip` in `cloudru_smoke.py`.

## AP-08: Don't drop `openssh-client` / `rsync` from `mle_kit_mcp/Dockerfile`

**What goes wrong**: Trimming the apk-add list in the runtime image.
**Why it's bad**: `tools/remote_gpu.py` shells out to `ssh` and `rsync` via
`subprocess` for both providers. The Alpine runtime only installs what's in the
explicit apk-add list; with these missing, the first `remote_bash` call crashes
with `FileNotFoundError: 'ssh'`. Latent because no smoke exercised the remote
path inside the container.
**What to do instead**: Any change to `mle_kit_mcp/Dockerfile` must keep both
packages in the runtime apk-add line.
**Mechanical guard**: `cloudru-smoke` (and any future `vast-smoke`) target.

## AP-09: Don't call the Vast SDK when `REMOTE_PROVIDER != "vast"`

**What goes wrong**: Reaching `vastai_sdk` from a non-vast code path.
**Why it's bad**: cloud.ru has no SDK. `vastai_sdk` calls crash on import (if not
installed) or worse — `destroy_instance(...)` against the externally-owned
cloud.ru instance id `0` is destructive against partner-team state. The Vast SDK
import was moved inside `get_sdk()`, and `cleanup_instance()` is gated by
`REMOTE_PROVIDER != "cloudru"`.
**What to do instead**: Any new vast-specific call (`get_offers`,
`wait_for_instance`, `check_instance`) must be reachable only via the `vast`
branch of `get_instance()`. See ADR-0006.
**Mechanical guard**: provider gating in `get_instance()`.

## AP-10: Don't delete Docker volumes without explicit approval

**What goes wrong**: Running `docker compose down -v` or `docker volume rm`.
**Why it's bad**: They wipe Langfuse trace history and persistent MCP state.
There is no off-site backup; once gone, historical traces are gone.
**What to do instead**: Ask the user before any volume-deleting command. `docker
compose down` (no `-v`) and `make stop-clean` are safe.
**Mechanical guard**: none — relies on the `.claude/settings.json` deny posture
and reviewer vigilance.

## AP-11: Avoid internal codenames in user-facing copy

**What goes wrong**: Leaking internal jargon (project codenames, legacy module
names) into agent outputs.
**Why it's bad**: It confuses downstream readers — both human and other agents —
and ages badly when the name no longer reflects behaviour.
**What to do instead**: Explain by purpose, not by name. README, error messages,
trace metadata, and final answers describe what something does, not what it is
called internally.
**Mechanical guard**: none yet — reviewer-checked.

## AP-12: Parallelise independent edits via sub-agents

**What goes wrong**: Editing several independent files sequentially in one
context.
**Why it's bad**: It is slower and lets unrelated edits bleed context into each
other.
**What to do instead**: Spawn one sub-agent per file via parallel `Agent` tool
calls in a single message; do not chain sequentially when there is no data
dependency. See user memory `feedback_split_tasks.md`.
**Mechanical guard**: none — a working practice, not a gate.

## AP-13: Don't commit secrets

**What goes wrong**: A real key landing in `.env_example`, `docker-compose.yml`,
or a doc.
**Why it's bad**: `.env` is gitignored, but adjacent files get edited together; a
real key in any tracked file is a permanent public leak.
**What to do instead**: Review staged diffs before commit.
**Mechanical guard**: none yet — CI has no secret scanner; `scripts/check-docs.sh`
and reviewer review are the current backstop.
