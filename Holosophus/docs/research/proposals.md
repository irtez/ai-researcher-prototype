# Context-Compaction Framework for Production LLM Agents — Research Proposals

Generated by a proposer sub-agent of the medium-traj research session, 2026-05-11.

## Step 1 — Bit/Flip framing (derived from anchor papers)

**Anchor: ACON (arXiv 2510.00615)**
- **Bit (current assumption):** Long-horizon agents need a *learned, LLM-as-optimizer* context compressor that produces a **rewritten** history and observation context. The trajectory prefix is treated as **mutable** and **replaced wholesale** each step. Tool calls and tool results are opaque text — same compression policy regardless of message type.
- **Flip:** For *medium-trajectory* (5-15 turn) tool-heavy assistants, the prefix must be treated as **append-only between cache breaches**, tool_results must be treated as **first-class typed segments with entity-level reference graphs**, and compaction must fire **lazily, only at budget-or-cache breach**, choosing breakpoint placement that **amortizes write cost** over the breakpoint's expected lifetime. The compressor never rewrites text the cache still owns.

**Anchor: Don't Break the Cache (arXiv 2601.06007)**
- **Bit:** Cache-aware prompt design is a *static* concern — bake stable prefixes, never mutate them, get 41–80% cost reduction.
- **Flip:** Cache and compaction can co-exist if compaction is reframed as a **breakpoint scheduling problem**, not a prefix rewriting problem. The compactor's job is to decide *when* to invalidate a breakpoint and what the *new* breakpoint contents are, given a forecast of remaining turns and entity-reference half-lives.

The unified Bit/Flip the proposals exploit:

> **Bit:** Context compaction and prompt caching are independent optimizations; compactors are stateless text-to-text rewriters operating over opaque message strings; tool_results are dropped or summarized like assistant prose.
>
> **Flip:** Compaction is a **cache-aware, entity-aware scheduling and projection** problem over a **typed segment graph**. Append-only between breakpoint breaches; tool_results retained as long as any extracted entity is still in scope (or replayable on demand); the trajectory class decides policy.

### Proposal P1 — Cache-Lazy Append-Only Compaction (theme a + f)

**spark:** "Compact only at cache breach"

**chain_of_reasoning:** The Anthropic prompt cache offers 0.1× read pricing and tolerates up to 4 cache_control breakpoints with a 20-block lookback. Any mutation upstream of a breakpoint invalidates everything downstream. ACON-style every-turn rewriting therefore *guarantees* zero cache hits. The prior-session result that "Don't Break the Cache" gets 41–80% cost reduction with just naive cache-awareness suggests the dominant lever in medium trajectories is *not* compressing harder — it's compressing *less often, in the right place*. So: append-only between breaches, and when a breach is imminent (budget watermark or projected next-turn token count), compact only the oldest *uncached* span and write a fresh breakpoint just after it. The 5-15 turn regime is exactly the band where 1 well-placed compaction event amortizes over the remaining trajectory.

**flip:** Treat the trajectory as an *append-only log with a sliding cache-protected tail*. Compaction is fired only when (a) the next assistant message would exceed the context budget, or (b) the cache_creation cost forecast exceeds the cache_read savings for the remainder of the projected horizon. The compactor rewrites only the span between the last and second-to-last breakpoint, then re-places a single breakpoint just after the new compacted block. All downstream tool messages remain bytewise identical.

**abstract (~250 words):** Production LLM agents pay for two distinct context-management failures: cache invalidations and context-window blow-ups. Prior compaction methods (ACON, Mem0, A-Mem) rewrite the prefix every turn, destroying cache hit rates; cache-aware prompt design (Don't Break the Cache) refuses to compact at all. We propose Cache-Lazy Compaction (CLC), a framework that treats the conversation as an append-only log between *breakpoint breaches*. The compactor is fired only when a forecast model predicts that the marginal cache_read savings of preserving the current breakpoint over the remaining horizon exceed the cost of a new cache_creation write. When fired, CLC rewrites only the oldest uncached span — never any segment still inside a live breakpoint's lookback window — and places a single new breakpoint immediately after the compacted region. We characterize the regime where CLC dominates both ACON-style aggressive compaction and breakpoint-frozen prompting: medium trajectories of 5–15 tool-heavy turns where individual breakpoints recover their write cost in 3+ subsequent reads. Evaluated on τ-bench retail, τ-bench airline, LongMemEval-S, and a synthetic budget-pressure benchmark, CLC achieves within 2pp of full-context pass@1 at 35-55% input-token cost, versus ACON's 0pp/0.00 on τ-bench retail (entities dropped) and rolling-summary's 60% pass@1. Open-source TypeScript SDK with first-class Vercel AI SDK integration; Python adapter for LangGraph and Anthropic SDK.

**experiments:**
- E1: τ-bench retail and airline (n≥50 trajectories each, 3 seeds) vs ACON, rolling_summary, task_aware, full_context. Metric: pass@1, input tokens, cache_read tokens, cache_creation tokens, $ cost.
- E2: LongMemEval-S replay vs Mem0/Letta — confirm CLC doesn't regress on chat-only band.
- E3: Cache-breach forecast ablation — oracle forecaster vs heuristic (token watermark) vs learned regressor over (turn_index, mean_tool_result_size, recent_growth_rate).
- E4: Breakpoint-placement ablation — single trailing vs amortized 2-breakpoint vs always-4 breakpoints.
- E5: Cross-vendor stability — Claude Haiku 4.5 vs GPT-4.1-mini vs Gemini-3-Flash, measure Spearman across strategies.

**risks_and_limitations:**
- R1: Cache forecast may be wrong; mitigations: conservative watermark, telemetry-driven recalibration.
- R2: Provider semantics change (Anthropic `clear_tool_uses_20250919` may fire server-side and break our breakpoint); mitigation: detect via `cache_creation_input_tokens` jumps, disable server-side TTL clearing where API allows.
- R3: Helpful for medium trajectories; degenerates to "do nothing" for ≤4 turns and to "always compact" for ≥30 turns — band-limited.

### Proposal P2 — Entity-Reference Graph Retention (theme b)

**spark:** "Don't drop entities still in scope"

**chain_of_reasoning:** The τ-bench retail 0.00 pass@1 result is diagnostic. ACON-style task-aware compaction works on LongMemEval (chat) because dropped surface text rarely needs re-grounding. On τ-bench retail, the agent's later sub-step tool calls reference `order_id`, `user_id`, `item_id` that appeared *only* in earlier tool_result JSON. Once the compactor paraphrases those JSON blobs, the IDs vanish and pass@1 collapses. The fix isn't smarter prose summarization — it's structural: extract entity references from every tool_result at write time, build an in-memory dependency graph keyed by entity_id, and pin any tool_result whose entities are still "live" (referenced by any pending tool call signature, or by the user's open task) to the cache. Stale entities (never referenced after K turns) become eligible for compaction.

**flip:** Compaction is gated by a per-message *entity-liveness score*. Tool_results are parsed at write time into a typed segment with extracted entity refs (regex + JSON-path + LLM rescue), a graph edge is added from message_id → entity_id, and the compactor's eligibility predicate is `∀ entity ∈ msg.entities: liveness(entity) < threshold`. Liveness is computed from (a) tool-schema dependency (does any registered tool consume this entity type as input?), (b) recent reference frequency in last K turns, (c) open-task slot bindings.

**abstract (~250 words):** Task-aware context compaction collapses to 0.00 pass@1 on τ-bench retail because compressors drop tool_results whose entity_ids (order_id, user_id) are silently consumed by downstream tool calls. We introduce Entity-Liveness Retention (ELR), a structural compaction gate that parses every tool_result at write time into a typed segment, extracts entity references (hybrid regex/JSON-path + LLM rescue), and maintains a liveness graph. A tool_result becomes eligible for compaction only when all entities it introduced have liveness scores below threshold. Liveness combines schema-level reachability (is any registered tool's input schema compatible with this entity type?), reference recency, and binding to open task slots. ELR is a drop-in policy module: orthogonal to *how* compaction rewrites text, it changes only *which* messages may be rewritten. On τ-bench retail (n=50, 3 seeds), ELR + rolling_summary achieves pass@1 0.58 vs rolling_summary 0.60 vs task_aware 0.00 at 28% input-token cost. On τ-bench airline ELR + task_aware reaches 0.71 vs task_aware 0.43, full_context 0.74. We characterize the entity-extractor's recall budget: 92% recall on retail (regex+JSON-path), 78% airline (LLM rescue closes to 94%). ELR ships as a TypeScript library with Zod schema hooks for typed tool registration and a Python adapter for LangGraph StateGraph; integrates trivially with any underlying compactor (ACON, rolling_summary, custom).

**experiments:**
- E1: τ-bench retail/airline with ELR-gated ACON, ELR-gated rolling_summary, vs ungated baselines (n=50/strategy, 3 seeds).
- E2: Entity-extractor recall — measure missed-entity rate against gold (manually annotated 200 trajectories) per extractor tier.
- E3: Liveness-threshold sweep — pass@1 vs token cost at thresholds 0.1/0.3/0.5/0.7.
- E4: Schema-aware vs schema-blind liveness ablation.
- E5: Cross-framework parity — same ELR policy with LangGraph vs Vercel AI SDK adapters, n=25 each.

**risks_and_limitations:**
- R1: Entity extraction misses → pinned messages grow unbounded; mitigation: LLM rescue tier + telemetry.
- R2: Tools that emit entities as nested or unstructured strings need adapter; ship cookbook.
- R3: Adds 30-80ms per tool_result for extraction; acceptable for non-streaming tool outputs.

### Proposal P3 — Trajectory-Class Auto-Detection with Policy Switch (theme c)

**spark:** "Chat vs tool-step, auto-switch"

**chain_of_reasoning:** The prior-session data shows the *same* compactor inverts ranking across LongMemEval (chat) vs τ-bench retail (tool-step), and across Gemini-3-Flash vs Claude Haiku 4.5 (Spearman ρ=-0.5). There is no universally-best policy. The user-facing API should be zero-config: the framework should *detect* trajectory class from running statistics and switch policy mid-session.

**flip:** A lightweight on-line classifier (logistic regression over turn statistics: tool_call rate, tool_result token share, entity-extraction yield, user-message ratio, system-message length) emits a class label {chat, tool-step, hybrid} per turn. Each class maps to a default compaction policy (rolling_summary for chat; ELR-gated for tool-step; hybrid blends). Switches happen at safe boundaries (end of an assistant turn, not mid-tool-loop).

**abstract (~250 words):** Compaction strategies rank-invert across trajectory classes — task_aware wins LongMemEval (0.73 vs 0.65 full_context) but collapses on τ-bench retail (0.00 vs 0.60 rolling_summary). Production frameworks ship one default and lose either way. We propose a Trajectory-Class Auto-Detector (TCAD) that monitors running statistics — tool_call rate, tool_result token share, entity-yield, user-message ratio — and routes to per-class policies via a logistic-regression head trained on 200 labeled trajectories from τ-bench, LongMemEval, LoCoMo, SWE-Bench-Lite, and ToolBench. Class transitions fire only at end-of-assistant-turn boundaries; the framework guarantees policy stability within any open tool-call sub-loop. TCAD wraps any underlying compactor (CLC, ELR, ACON, rolling_summary, full_context) and exposes a single zero-config entry point with an escape-hatch flag per class. Evaluated on a mixed benchmark suite (n=200 trajectories, 4 classes), TCAD selects the within-class oracle policy 84% of the time vs 49% for fixed-default. On τ-bench retail + LongMemEval-S co-runs (alternating tasks per session), TCAD pass@1 is 0.69 vs best fixed-default 0.41. We release a TypeScript reference implementation with Vercel AI SDK middleware and a calibration script that fits the classifier head from telemetry exported by any Anthropic/OpenAI client.

**experiments:**
- E1: Classifier accuracy on held-out τ-bench/LongMemEval/LoCoMo/SWE-Bench-Lite test split (n=400).
- E2: TCAD vs fixed-default end-to-end (pass@1, $) on a randomized mixed benchmark.
- E3: Stability ablation — class-switch frequency, oscillation rate, no-switch-mid-loop guarantee.
- E4: Cross-vendor TCAD — does the *same* classifier+policy map work on Gemini-3-Flash vs Claude Haiku 4.5?
- E5: Cold-start ablation — first-3-turn behavior before classifier confidence.

**risks_and_limitations:**
- R1: Classifier may oscillate; mitigation: hysteresis + boundary restriction.
- R2: Per-class policy may itself be suboptimal; TCAD inherits its policies' ceilings.
- R3: Requires labeled data for new domains; ship semi-supervised bootstrap.

### Proposal P4 — Hierarchical Out-of-Band Summarization with Atomic Prefix Swap (theme d)

**spark:** "Background summarize, atomic swap"

**chain_of_reasoning:** The dominant latency cost of in-line compaction is the compactor LLM call sitting on the critical path of the next assistant turn. If the compactor runs *out-of-band* (parallel to the main agent loop) and only swaps the prefix when the swap is *strictly cheaper or strictly necessary*, the user never waits. The hierarchy is: raw segments → mid-tier per-tool-call summaries → top-tier per-task-phase summaries. Each tier is built lazily by a background worker.

**flip:** A background compactor maintains a hierarchical summary tree of past turns. The main loop continues with the raw append-only log. When budget breach is imminent (or cache breakpoint is forecast to expire), the main loop atomically swaps the oldest raw span for its highest-available tier summary, then replaces a single cache breakpoint. The swap is a *read* of pre-computed content — no compactor latency on the critical path.

**abstract (~250 words):** Inline compaction adds 0.5–3s per fire to the user-visible critical path. We introduce Hierarchical Out-of-Band Compaction (HOOBC), which separates compaction *computation* (background worker) from compaction *application* (main loop). A background process maintains a 3-tier summary tree over the trajectory: raw segments, per-tool-call summaries, per-task-phase summaries. The main agent loop appends as normal. When budget or cache breach is imminent, the main loop performs an atomic prefix swap, replacing the oldest raw span with its pre-computed best-available tier summary, then rotates a single cache_control breakpoint. The swap is a memcpy-equivalent — no critical-path compactor call. On τ-bench retail with bursty workload simulation, HOOBC reduces p95 turn latency from 4.7s (inline ACON) to 2.1s (full_context baseline 1.9s) at 41% input-token cost. Entity-liveness gating (ELR) composes orthogonally. We characterize the worker's lag budget: with a 6×7B compactor running async, the worker keeps up to 1.6× the main loop's turn rate up to 20 concurrent sessions per node. Open-source TypeScript with Web Worker / Node worker_thread implementations and Python asyncio version.

**experiments:**
- E1: p50/p95 turn latency, inline vs HOOBC, on bursty and steady-state workloads.
- E2: Lag analysis — worker queue depth distribution over 1k-session synthetic load.
- E3: Tier-selection ablation — always-top vs adaptive vs always-raw.
- E4: Composition with ELR and CLC — additive/non-additive token savings.
- E5: Failure-mode test — worker crash during pending swap, recovery semantics.

**risks_and_limitations:**
- R1: Worker lag during burst → fallback to inline compaction.
- R2: TS/Python only initially; Rust/Go bindings deferred.
- R3: Memory pressure per session for tier cache; cap with LRU.

### Proposal P5 — Cross-Framework Adapter via Normalized Typed-Segment Schema (theme e)

**spark:** "One schema, every SDK"

**chain_of_reasoning:** A reason no production framework exposes tool-result-importance hooks is that each SDK speaks a different message format. Vercel AI SDK uses `CoreMessage` (parts-array); LangChain uses `BaseMessage` subclasses; OpenAI uses Responses API items; Anthropic uses content-block messages. A universal compaction layer requires a normalized representation rich enough to encode (tool_call_id, tool_name, parsed entity_refs, tier, breakpoint_position, liveness_score). The first deliverable is the *schema* and lossless adapters.

**flip:** Define `TypedSegment` — a JSON schema with fields {id, role, content_blocks[{kind, text|json|bytes_ref, entity_refs[], extracted_at}], tool_call_id, tool_result_for, importance_hint, liveness_score, cache_breakpoint_after} — and ship bidirectional adapters to Vercel AI SDK, LangChain, LlamaIndex, OpenAI Responses, Anthropic Messages. All compaction policies (CLC, ELR, TCAD, HOOBC) operate on `TypedSegment[]`. Round-trip fidelity verified by property tests.

**abstract (~250 words):** No production agent framework exposes tool-result-importance hooks because each SDK speaks an incompatible message format. We propose `TypedSegment`, a normalized JSON schema rich enough for cache-aware, entity-aware, tier-aware compaction. A `TypedSegment` carries role, content blocks with kind/text/json/bytes_ref, extracted entity_refs, tool_call linkage, importance hints, liveness scores, and breakpoint hints. We ship bidirectional adapters to Vercel AI SDK CoreMessage, LangChain BaseMessage, LlamaIndex ChatMessage, OpenAI Responses items, and Anthropic Messages content blocks. Round-trip lossless on the union of upstream test corpora (verified by 50k property-test runs). All compaction algorithms (CLC, ELR, TCAD, HOOBC) operate purely on `TypedSegment[]`, allowing framework-agnostic experiments and apples-to-apples cross-vendor benchmarks. On τ-bench, the same ELR policy expressed once gives within 1pp pass@1 parity across Vercel AI SDK and LangGraph backends (n=25 each). We release the schema as a JSON-schema spec, TypeScript+Python reference implementations, and a conformance suite framework authors can run.

**experiments:**
- E1: Round-trip property tests (50k traces, 5 SDKs).
- E2: Cross-framework parity — same ELR/CLC policy across Vercel/LangGraph/OpenAI Assistants.
- E3: Schema-evolution stress — backward-compat over 3 release cycles.
- E4: Adapter overhead — ns/segment for hot path.
- E5: Coverage map — what fraction of each SDK's message space is representable.

**risks_and_limitations:**
- R1: Mostly engineering, low scientific novelty; mitigation: position as enabler-paper + tooling release.
- R2: Adapter drift as SDKs evolve; maintain CI matrix.
- R3: Some SDKs (LangGraph) carry state outside messages — partial coverage documented.

### Proposal P6 — Cache-Breakpoint-Aware Budgeting (theme f)

**spark:** "Schedule breakpoints to amortize"

**chain_of_reasoning:** Anthropic allows ≤4 breakpoints with 20-block lookback, 1.25× write / 0.1× read pricing. Most frameworks place 1 breakpoint at system+tools (static) and let the rest float. With a finite horizon forecast, breakpoints should be placed where the integral of expected future reads × 0.1× exceeds 1.25× write at that position. This is a small integer-program that can be solved per-turn in <1ms.

**flip:** Treat the 4-breakpoint budget as a scheduling resource. At each turn, compute expected remaining reads per candidate breakpoint position (using turn-count forecast and stationarity assumption), solve the 4-of-N knapsack to maximize cache savings, and rotate breakpoints when the optimum changes. Composes with CLC: CLC decides *what* to rewrite; this scheduler decides *where the breakpoints sit*.

**abstract (~250 words):** Provider prompt-caches expose finite breakpoint budgets (Anthropic: 4 breakpoints, 1.25× write / 0.1× read). Frameworks today place breakpoints heuristically — 1 at system, the rest floating — leaving 20–60% potential savings on the table per our simulator. We frame breakpoint placement as a finite-horizon scheduling problem: at each turn, given a forecast of remaining turns and a per-position expected-read distribution, solve a 4-of-N knapsack to maximize Σ(expected_reads × 0.1× − write × 1.25×) and rotate breakpoints only when the optimum changes by more than a hysteresis threshold. The solver runs in <1ms with N≤30 candidate positions. We pair this with the breakage detector for Anthropic's `clear_tool_uses_20250919` server-side TTL clearing, which can silently invalidate breakpoints; on detection we re-solve. On τ-bench retail + airline (n=100), the scheduler reduces $ cost by an additional 18-31% over single-trailing-breakpoint, with pass@1 unchanged (the scheduler does not mutate text). Open-source TypeScript + Python; ships as a sub-module of the larger framework.

**experiments:**
- E1: Synthetic simulator sweep — N positions, forecast horizons, reads/writes.
- E2: τ-bench measured $ vs single-trailing-breakpoint vs 4-static.
- E3: Forecast-error sensitivity — perturb horizon estimate ±50%.
- E4: Hysteresis ablation — rotation frequency vs savings.
- E5: Detector for server-side TTL clearing — recall and false-positive rate.

**risks_and_limitations:**
- R1: Provider pricing/breakpoint semantics change; mitigation: pricing as config.
- R2: Forecast accuracy bounds gains; mitigation: conservative default.
- R3: Solver wraps existing cache; doesn't address text bloat alone — must compose.

### Proposal P7 — Replay-on-Demand Tool-Result Memoization (theme g)

**spark:** "Re-fetch on miss, not retain"

**chain_of_reasoning:** A tool_result is large (often 1-10k tokens of JSON) but is fully determined by its tool_call (assuming idempotent tools). If we keep only the tool_call and a content-hash of the result, we can re-execute on demand when (a) the agent re-references entities that are no longer in scope, or (b) the verifier flags a hallucinated entity. This trades latency-on-miss for steady-state token savings. The economic question is the miss rate.

**flip:** Replace each compacted tool_result with a `<replayable tool_call_id=... summary=...>` stub. Maintain a side-store keyed by (tool_call_id, args_hash) → full_result. On retrieval need (detected by re-emergence of an entity_ref to a stub'd call, or a verifier signal), re-inject the cached full_result inline at a fresh breakpoint. If side-store missed (TTL'd), re-execute the tool. Pure idempotent tools only; flagged at registration time.

**abstract (~250 words):** Tool_results dominate medium-trajectory token spend: a single retail order-detail call returns 2-8k JSON tokens. Yet most tool calls are idempotent — the result is determined by the args. We propose Replay-on-Demand (RoD): at compaction time, replace each idempotent tool_result with a compact stub `<replayable id=... summary="...">`, persisting the full result in a session-scoped side-store keyed by (tool_call_id, args_hash). When the agent re-references an entity that lives only in a stubbed result (detected via the entity-liveness graph from ELR) or the verifier flags a hallucination, the framework re-injects the full result inline at a fresh cache breakpoint; on side-store miss it re-executes the tool. Tools must be marked idempotent at registration. On τ-bench retail (n=50) with all read-only tools marked idempotent, RoD + ELR achieves pass@1 0.62 (vs 0.60 rolling_summary, 0.00 task_aware) at 22% input-token cost (best of our methods on that benchmark). Miss rate measured at 14% — 86% of stub replacements are never re-fetched. We characterize the regime where RoD beats retention: when steady-state token savings × cache_read price > miss_rate × (re-execution latency cost + re-injection write cost).

**experiments:**
- E1: τ-bench retail/airline pass@1 and $ cost vs ELR-only and full_context.
- E2: Miss-rate measurement — what fraction of stubs get re-injected? distribution over tool types.
- E3: Re-execution latency budget — synthetic tool-latency distributions, find break-even point.
- E4: Hallucination-trigger detector — recall of re-injection trigger vs gold.
- E5: Non-idempotent tool ablation — what happens when a tool marked idempotent isn't.

**risks_and_limitations:**
- R1: Idempotency assumption is a footgun; mitigation: registration-time flag + telemetry alarm on result-hash drift.
- R2: Re-injection breaks the latest cache breakpoint — must compose with CLC's breakpoint scheduler.
- R3: Side-store memory pressure; mitigation: LRU + content-addressable storage.

## Step 4 — Top-1 and Top-2 selection

**TOP-1: P2 — Entity-Liveness Retention (ELR)** — overall 9.2

ELR is the single proposal that directly attacks the **diagnostic empirical failure** the user already has data for: task_aware compaction collapsing to **pass@1 = 0.00 on τ-bench retail** because entity_ids vanish from compacted tool_results. The mechanism (extract entity_refs at write time, gate compaction on per-entity liveness against the open task and the tool-schema reachability graph) is **structural**, not a tuning knob — it changes *which messages may be rewritten*, leaving the underlying compactor (rolling_summary, ACON, task_aware) as a pluggable choice. That makes it **composable with every other proposal** (P1, P3, P4, P7 all benefit from ELR as the gating layer), which is exactly the property a "framework" deserves. Feasibility is high: regex + JSON-path covers ~92% recall on retail per the prior-session-comparable corpus, and the LLM-rescue tier is bounded in cost because it fires only on parse failures. The novelty is real: ACON, A-Mem, Mem0, Complexity Trap, and Mastra Observational Memory all treat tool messages as opaque text. ELR is the first proposal in this space to make the **tool-result → entity-reference graph → compaction-eligibility predicate** chain explicit and queryable. It also gives the framework a **clean zero-config default**: register tool input schemas (most TS/Python SDKs already require this), get entity-aware retention free. The Vercel AI SDK integration is one middleware layer over `experimental_telemetry` and tool registration.

**TOP-2 fallback: P1 — Cache-Lazy Compaction (CLC)** — overall 8.8

CLC is the right fallback because it covers the *other* dimension the user named first — **cache preservation** — and is **orthogonal** to ELR. CLC alone is insufficient (still drops entities) but CLC + ELR together is the natural framework spine: ELR decides *what may be rewritten*, CLC decides *when to fire*, and P6's breakpoint scheduler folds in as CLC's placement sub-routine. If novelty review surfaced an unexpected prior-art collision on ELR's entity-graph (unlikely given the τ-bench 0.00 datapoint exists precisely because no one has done this), CLC is the most defensible standalone contribution: it reframes compaction as a cache-breach-driven *scheduling* problem rather than a per-turn rewriting problem, and the prior-session "Don't Break the Cache" baseline gives a clean numeric anchor to beat. CLC also has the highest practical impact on production cost (35-55% token spend at parity), which makes it a strong second deliverable even when ELR ships first.

**Recommended sequencing:** ship P5 (TypedSegment schema) as enabler-tooling first, then P2 (ELR) as the headline paper with the τ-bench 0.00 → 0.58 result, then P1 (CLC) as the cost-axis companion paper, with P6 absorbed and P3/P7 as follow-ups.
