# Удалённое исполнение в химическом профиле

Химический профиль Claude Code поддерживает `Local`, `GPU` и `Auto`.
По умолчанию выбирается `Local`. В UI режим задаётся в настройках запуска,
в CLI — `--compute-mode Local|GPU|Auto`. При доработке используется сохранённый
режим сессии.

- Local предоставляет локального экспериментатора с Docker Bash и локальными
  инструкциями; удалённые инструменты химического профиля запрещены.
- GPU предоставляет `mle-solver-remote` с химическими инструкциями и средствами
  удалённого выполнения. Менеджер и файловые native-инструменты работают локально.
- Auto предоставляет оба варианта; менеджер выбирает исполнителя по ресурсам
  и окружению, необходимым задаче. Сам по себе запрос к PubChem, ChemX или ADMET
  не требует удалённой машины.

Инструкции режима находятся в `prompts/shared/execution.yaml` под каноническим
каталогом промптов. Химическая удалённая роль —
`prompts/profiles/chemistry/mle_solver_remote.yaml`. Общий профиль использует
прежнюю удалённую роль с тем же контрактом передачи файлов. Выбранные согласования
источников и плана применяются до вычислений, включая удалённого экспериментатора.

## Подготовка узла

MLE Kit использует существующую настройку `REMOTE_PROVIDER`:

- `cloudru` и `selectel`: заранее подготовленный SSH-узел, адрес, пользователь,
  порт, ключ и домашний каталог задаются соответствующими переменными;
- `vast`: существующий экземпляр либо аренда по заданным GPU и диску. Первый
  вызов удалённого инструмента может создать платный экземпляр. При недоступности
  указанного существующего экземпляра прежняя реализация может перейти к аренде.

Эти параметры задаёт оператор, не агент. Машина переиспользуется процессом MCP;
её жизненный цикл не совпадает с отдельной итерацией исследования. Условия
вычислительного окружения и изоляции заранее обеспечиваются на выбранном узле.
Новая адаптация не развёртывает дополнительный Docker внутри произвольного SSH-хоста.
До запуска проверьте параметры существующего провайдера и доступные ресурсы.

Для конфигурации с изолированным исполнением пользовательского кода SSH должен
вести в Docker-контейнерное окружение. При создании нового экземпляра Vast.ai
используется заданный Docker-образ; для готового узла контейнер и SSH-доступ
к нему подготавливает оператор. Это условие также относится к повторно
используемому существующему экземпляру. Сам remote_bash не определяет, ведёт
ли SSH внутрь контейнера, и не создаёт контейнер на произвольном узле.
Обычный SSH-доступ к хосту подходит для проверки транспорта, но не подтверждает
контейнерную изоляцию вычислений.

## Файлы

Для каждого `session_id` удалённые инструменты используют
`<remote_home>/sessions/<session_id>/`. `remote_bash` начинает каждую команду
в этом каталоге; переменные оболочки и `cd` между отдельными вызовами не сохраняются.
Файлы остаются на узле. Привязка к сессии подставляется общей проверкой MCP-вызовов.

1. `remote_upload(file_path="inputs/data.csv")` переносит локальный входной файл
   в одноимённый относительный путь удалённой сессии.
2. `remote_text_editor` готовит код, например `mle/code/analyze.py`. Локальная
   копия редактора и удалённый файл относятся к этой же сессии.
3. `remote_bash` запускает программу; неуспешный код завершения возвращается
   как ошибка с выводом команды.
4. `remote_download(file_path="mle/results/result.json")` возвращает результат
   в ту же относительную папку локальной сессии. После этого файл виден менеджеру
   и UI. Скачивайте также нужные код, промежуточные результаты и контрольные точки.

Пути передачи относительные; переходы `..`, абсолютные пути и локальные ссылки
за пределы сессии отклоняются до обращения к машине. Загрузка всего общего
каталога `.py` при каждом подключении удалена: передача входов выполняется явно.
Для старых прямых клиентов без session_id сохраняется работа от remote_home;
новые агентные запуски передают session_id. `llm_proxy_remote` также размещает
свой скрипт и файлы запуска в удалённом каталоге сессии.

Химические MCP-сервисы и серверные наборы данных остаются на своих узлах.
GPU-режим переносит пользовательские вычислительные программы, а не ADMET-сервис.

## Границы проверки

Проверки ролей/согласований и файловых инструментов не требуют LLM или аренды.
`tests/test_remote_sessions.py` подставляет SSH/облако и проверяет реальные
локальные файлы, маршрутизацию, ошибки и разделение сессий. Проверку на настоящем
удалённом узле и модельный сценарий согласуют отдельно; наличие режима в UI
само по себе не подтверждает доступность настроенной машины.

`tests/remote_workspace_ssh_probe.py` проверяет настоящий SSH/rsync на
одноразовом локальном Docker-узле: две сессии, имена с пробелами/кавычками,
загрузка кода, выполнение, возврат файлов размером 11 МиБ и ненулевой код
завершения. Облако и GPU в этой проверке не используются.
