# Согласования этапов и доработка результатов

Настройки и действия одинаковы для профилей `general` и `chemistry` в контуре
Claude Code. Phoenix и Langfuse также подключаются через общий код запуска.

Постоянные инструкции и шаблоны этапов находятся в
`holosophos/holosophos/prompts/shared/approvals.yaml`. Python выбирает блоки
по настройкам/состоянию итерации и подставляет пути; механическая блокировка
операций остаётся в `scripts/approval_control.py`. При выключенных
согласованиях эти инструкции и инструмент `request_approval` не подключаются.

## Настройки задачи

В блоке «Согласования» независимо включаются выбор источников и план
исследования. По умолчанию оба этапа выключены. Можно включить автоматическое
согласование через положительное целое число секунд; начальное значение
поля — 300, но до включения таймер не действует. Один интервал применяется
к выбранным этапам. Без таймера система ждёт решения до остановки или ошибки.

При выключенных этапах runner не добавляет инструмент `request_approval`,
инструкции согласования и соответствующий hook. При включении настройки
действуют на текущую итерацию сессии. Их можно изменить перед следующей
доработкой, когда сессия не выполняется.

## Что согласуется

| Этап | Содержание | До каких исполнителей требуется |
|---|---|---|
| Источники | Входные данные, источники и область поиска; найденный список статей ещё не требуется | librarian, proposer и все последующие роли |
| План | Предлагаемые действия и ожидаемые результаты | локальный/удалённый экспериментатор, writer, reviewer |

Менеджер может подготовить источники сам и поручить proposer разработать
план до его согласования. Сценарий без экспериментов проходит согласование
плана перед writer. Краткий план небольшой правки менеджер составляет сам:
генерация и оценка новых исследовательских идей для этого не требуются.
Выключенные этапы не проверяются.

Runner создаёт `plans/<id>/` и `sources/<id>/` и передаёт пути менеджеру.
План сохраняется в Markdown внутри каталога текущей итерации; имя файла
и вложенные папки свободные. Например, `stage="plan"` и
`document_path="plans/0002/comparison.md"` при `PLAN_DIRECTORY: plans/0002`.
Вызов `request_approval(stage, document_path)` регистрирует конкретный документ.
Модель получает короткую строку решения («Согласовано.», «Нужно доработать.»
и т. п.) и текст замечания, если он есть. JSON со снимком документа, digest и
служебными полями хранится для истории/UI, но не возвращается целиком в контекст.
Стандартные вопросы согласования в русскоязычном UI также показаны по-русски.

Контекст итерации описывает инструменты по этапам и учитывает включённые
галочки. Известные файлы читаются через `Read`, Markdown готовится через native
`Write/Edit`. Каталоги итерации уже созданы системой; обход пустых папок перед
записью документа не требуется. Bash, включая начальный `ls` или `mkdir`,
ожидает всех включённых согласований.

Если нужен поиск файлов, менеджер загружает через `ToolSearch` инструменты
`mcp__mle_kit__use_glob` / `mcp__mle_kit__use_grep`. Они работают относительно
общего MCP workspace: `path` должен содержать ID сессии, при необходимости
с подпапкой. Контекст даёт точное значение. Перед чтением через native `Read`
возвращённый путь переводится в относительный путь внутри сессии. Описания
MCP-инструментов также объясняют эту разницу. Образ MLE Kit сохраняет `ripgrep`
как рабочую зависимость после удаления сборочных пакетов.

Наличие native `Glob/Grep` зависит от сборки CLI. Их разрешение в hook не
добавляет отсутствующий инструмент: модель должна ориентироваться на выданные
определения. Подсказка CLI заменить отсутствующий поиск на Bash не отменяет
ожидания согласования. При выключенных согласованиях этот блок не добавляется.

Прежний путь плана не принимается за план новой доработки; неизменённый
согласованный документ источников можно использовать повторно.
Допускается абсолютный путь внутри той же папки. Отсутствующий, пустой,
неподходящий файл или путь за пределы сессии возвращает ошибку менеджеру.

UI показывает одну карточку со снимком документа. Доступны «Согласовать»
либо замечание и «Отправить корректировку». Корректировка возвращается
менеджеру; он меняет документ и предлагает новую версию. `ask_human`
остаётся отдельным инструментом обычных уточнений и не подтверждает этапы.

Hook перед всеми вызовами инструментов проверяет нужные разрешения,
принадлежность плана текущей открытой итерации и соответствие файла
согласованному содержимому. Если разрешения нет, менеджер получает краткую
инструкцию подготовить документ и запросить согласование. Сам отказ не
создаёт карточку. Изменение согласованного файла отзывает разрешение;
пересмотр источников также отзывает согласование плана. Неизменённый
план не требует повторной карточки внутри той же итерации; следующая
доработка всегда требует нового плана и разрешения, если галочка включена.

## Таймер и восстановление карточки

Дедлайн хранится на сервере отдельно для каждого запроса. Обновление или
закрытие вкладки его не сбрасывает. Автоматическое решение помечается
`auto_approved` и отличается от ответа человека. Уже принятое решение
нельзя заменить поздним ответом; ответы адресуются конкретному `qid`.
Изменение документа во время ожидания отменяет запрос к прежней версии.
Остановка или техническая ошибка не означает согласия.

Ожидающая карточка восстанавливается при выборе сессии. Настройки другой
задачи не изменяют её содержание или дедлайн.

## Замечания к готовому результату

В завершённой сессии кнопка «Доработать» раскрывает поле замечания и настройки
согласований. «Свернуть» скрывает редактор, сохраняя введённый текст и галочки
до закрытия страницы или смены сессии. Само раскрытие ничего не запускает:
отправка заполненной формы начинает новую итерацию той же беседы Claude Code
в той же папке. После успешного завершения форма снова сворачивается. Ошибка
отправки сохраняет редактор и введённые значения для повторной попытки. Число последовательных
итераций не ограничивается. Исходная постановка и SDK ID сохраняются;
профиль, модель, вычислительный режим и политика восстанавливаются.

Каждое замечание к завершённому результату требует отдельного Markdown-плана
в `plans/<id>/`, включая простую правку: достаточно нескольких строк.
Старые планы сохраняются. При включённом согласовании менеджер получает
разрешение текущей итерации; при выключенном ожидания и инструмента нет,
но сам краткий план всё равно нужен. Runner проверяет его перед успешным
завершением. После завершения можно отправить следующее замечание. Во время
работы сохраняется прежнее управление пауза/продолжение/steer/остановка.

До нужного разрешения hook допускает Read, указанные выше MCP-поиски,
просмотр ресурсов, список задач и native Write/Edit Markdown в подготовительных
каталогах. Native Glob/Grep также разрешены, если CLI действительно их выдал.
Химический `read_data_file` также может прочитать загруженную таблицу для
подготовки документа источников. Получение готовых данных PubChem, поиск
ChemX и `search_connected_datasets` доступны после согласования источников,
до согласования плана. Расчёт дескрипторов и построение аналитического отчёта
к таким подготовительным чтениям не относятся.
Поиск литературы и генерация предложений доступны после выбранного согласования
источников. Bash, расчётные MCP и запись результата блокируются до разрешения.
Librarian/proposer сохраняют литературные и планировочные инструменты;
вызов другого исполнителя из подготовительной роли также проверяется.
Если SDK не передал сведения о подготовительной роли, привилегии такой роли
не предполагаются. Разрешённые пути и операции описаны в `ApprovalGate`.

Техническое продолжение сохраняет итерацию и её разрешения. Сообщение менеджеру
указывает действующий согласованный документ; создавать новый план или
повторную карточку только из-за resume не требуется. Если файл изменился,
сообщение и hook снова требуют согласования. После завершения
план становится историческим решением; старый hook, вопрос или таймер не
дают разрешение новой итерации. Политика фиксирована: попытка изменить
галочки/таймер через CLI `--resume` отклоняется. Новую политику выбирают
перед новой пользовательской доработкой.

Одновременно выполняется одна итерация сессии, включая очередь. Закрытие
браузерного потока не освобождает работающий процесс для повторного запуска.
Если сохранённой SDK-беседы нет, возвращается явная ошибка. Ошибка доработки
не перезаписывает предыдущий `result.md` пустым ответом.

## API и CLI

`POST /agents/manager` принимает `approvals` и `resume`. При `resume=true`
последнее пользовательское сообщение — замечание; `session_id` прежний.
Отсутствие `approvals` при доработке сохраняет настройки. Явная конфигурация
имеет приоритет над прежним `hitl`; `hitl=true` означает два включённых
этапа без таймера.

```json
{"approvals":{"sources":true,"plan":true,"auto_approve_after_seconds":null}}
```

`GET /agents/session/{id}` возвращает настройки, активность, возможность
продолжения и последнее решение. `GET /agents/question/{id}` возвращает
карточку с `qid`, `stage`, снимком в `context` и `auto_approve_at` в Unix
секундах; 204 означает отсутствие вопроса. `POST /agents/answer` принимает
`session_id`, `qid`, действие `approve|revise|answer` и текст для двух последних.
Проверяются владелец сессии, тип действия и актуальность вопроса.

В CLI `--hitl` включает оба этапа без таймера. `--approvals` принимает JSON
той же формы, что значение поля `approvals` в API; при `--resume` настройки
читаются из сессии. `--dump-prompts` показывает выбранные инструкции без
обращения к модели.

Runner также сохраняет [серверную историю итераций](research-iterations.md):
исходные сообщения, настройки, отдельные события, ответы и снимки результатов.
Она доступна через API независимо от браузерного кеша. Для каждой итерации
менеджер получает отдельный путь полного документа; финальное сообщение его
не подменяет. В `approval_state` хранятся этапы и решения с `iteration_id`,
`qid`, текстом снимка и способом ответа; в `plans` — файлы планов и их снимки.
Планы сохраняются и при штатно обработанной ошибке/отмене. История доступна
в UI через выбор итерации и блок «Задача, планы и решения».

## Код и границы проверки

Общий механизм — `scripts/approval_control.py`; HTTP, продолжение и очередь —
`scripts/cc_runner.py`; CLI и существующий цикл пауз — `scripts/run_research.py`.
Состояние решений хранится в `.holosophus_ctl/approvals.json`, настройки —
`.holosophus_ui/settings.json`, беседа — прежний `session.json`.

Проверки без LLM: `tests/test_iteration_approvals.py`, `tests/test_approval_control.py`,
`tests/test_cc_runner_feedback.py` и существующие тесты управления запуском;
UI — `npm test` и `npm run build`. Малый запуск с настоящей моделью проводится
отдельно. Эти проверки не подтверждают качество исследовательского результата.

Hook контролирует делегации, прямые вызовы инструментов до разрешения и
снимок указанного файла. Он не устанавливает семантическое соответствие
произвольного кода плану и не заменяет изоляцию ОС после допуска исполнителя.
Актуализация документа при изменении смысла решения входит в инструкции менеджера.
